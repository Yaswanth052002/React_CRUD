# Story: AUTH-02 — Existing-user authentication and credential validation

**Epic**: AUTH
**Status**: Validated
**Priority**: P1
**Independent test**: true
**Owner**: Unassigned (backend/auth workstream — to be assigned by PO)
**Updated**: 2026-08-17

**Source**: intake:raw-input

## User story

As an existing user (Admin or Regular User) of the CRUD dashboard, I want to log in with my email and password so that I can access the dashboard as myself without a new account being created or my existing user record being duplicated. As the operator of this deployment, I need a controlled way to provision an initial credential for existing users who have none, so that legitimate accounts can actually reach the login flow above without ever relying on a hardcoded or guessable default password.

## Brownfield findings (read before implementing)

- `backend/app/models/user.py` was read directly. The `users` table currently has **no credential field** (no `password`, `password_hash`, or similar column) — only `id, name, email, phone, role, status, created_at, updated_at`.
- `backend/app/repositories/user_repository.py`, `backend/app/services/user_service.py`, and `backend/app/schemas/user.py` likewise have no auth-related logic — the layering is CRUD-only today.
- Consequence: no existing/seeded user can log in via the REAL backend today because the credential column doesn't exist yet — AUTH-03 must land before this story's REAL production behavior works end-to-end. However, this story's own acceptance criteria (AC1-AC3, the login-endpoint contract) are validated against a test-double credential store/verifier that presents the same hash-and-verify interface AUTH-03 will provide, so AUTH-02's validation and independent-test status do NOT wait on AUTH-03's real implementation landing — only genuine end-to-end production use does.
- **Provisioning is absorbed into this story's scope (resolved post-research, see Decision log)**: even once AUTH-03's schema/hashing lands, every pre-existing/seeded row still has no credential and no other story builds a way to give one. Rather than leaving this as an unscoped gap or spinning up a separate story, AUTH-02 owns a minimal, controlled provisioning mechanism (below) so that existing users can actually reach the login flow described in AC1-AC3.

## Acceptance criteria

1. Given a user record that already has a valid password credential set, when the user submits that email and the matching password on the login form, then the backend returns a successful authentication response (per AUTH-04 for token/session shape) and no new row is inserted into and no existing row is duplicated in the `users` table.
2. Given a user submits an email/password pair where the email does not exist OR the password does not match the stored credential, when the login request is processed, then the backend returns the same generic error message and the same HTTP status code in both cases (e.g. `401 Unauthorized` with body `"Invalid email or password."`), such that the response gives no observable signal (status code, message text, response timing bucket, or field-specific validation error) distinguishing "account does not exist" from "wrong password."
3. Given an existing user record whose `must_reset_password` flag is `true` (the state every seeded/pre-migration row is left in by the provisioning migration in AC4, until AC5's provisioning script has run for that specific user), when that user attempts to log in with any password, then the backend rejects the attempt using the same generic error message as AC2 (never a distinct "no password set" or "must reset" message) and does not silently authenticate them.
4. Given the one-time backend provisioning migration runs (once, at deploy/upgrade time — not exposed via any HTTP endpoint), when it completes, then every existing user row that has no `password_hash` value is assigned a cryptographically random, unusable password hash (produced via AUTH-03's hashing scheme — never a plaintext, guessable, or hardcoded default value) and its `must_reset_password` flag is set to `true`; running the migration a second time is a no-op for rows that already have a hash and `must_reset_password = false`.
5. Given an operator with direct server/database access needs to give a specific existing user a real initial password, when the operator runs the companion provisioning script (e.g. `python -m app.scripts.set_initial_password <email>`, invoked directly against the deployment — never exposed as an HTTP/API endpoint, and therefore not gated on anyone already being logged in), then that user's `password_hash` is updated to a securely hashed value of the operator-supplied password (the plaintext value is never logged, persisted anywhere but the hash, or echoed back by the script beyond the operator's own terminal), their `must_reset_password` flag is cleared to `false`, and they can subsequently log in per AC1.

## Non-functional requirements

- Performance: login endpoint responds within p95 < 400ms under 50 RPS (best-judgment default per `.claude/rules/performance-baseline.md`'s bounded-I/O guidance; no auth-specific NFR baseline exists in this repo today — see Decision log).
- Security: Per `.claude/rules/security-baseline.md`: applies to the login endpoint. Password verification uses the hashing scheme owned by AUTH-03 (argon2id/bcrypt); no plaintext password is ever logged or persisted. Rate-limit login attempts per `.claude/rules/security-baseline.md` (3/email/60min rolling, HTTP 429) to prevent credential-stuffing/enumeration. Error responses never reveal account existence (AC2/AC3). No hardcoded or invented default password is introduced anywhere in code, migrations, or seed data for provisioning existing users. The provisioning migration (AC4) never assigns a guessable value — the unusable hash is generated from cryptographically random bytes, not a fixed string. The companion provisioning script (AC5) is a local/server-side script requiring direct deployment access (not a network-reachable endpoint), so it introduces no new authenticated-attacker surface; it never writes the operator-supplied plaintext password to any log, database column, or file — only its hash is persisted.
- Accessibility: login form error messaging meets WCAG 2.1 AA (error text associated with the form via `aria-describedby`, announced to screen readers) — detailed UI AC owned by AUTH-01.
- Observability: log authentication attempts (success/failure) keyed by opaque `user_id` or hashed email only, per security baseline; emit a counter metric for failed-login rate to support the rate-limit threshold above.

## Dependencies

- Upstream: AUTH-03 (password security and server-side hashing) — supplies the schema migration adding the credential column and the real hashing/verification implementation. This story's own tests are validated against a stubbed hash-and-verify interface matching AUTH-03's contract (see "Test strategy" below), so implementation and validation of AUTH-02 do not require AUTH-03's real migration to land first; a follow-up integration check against the real implementation is required once AUTH-03 ships (tracked, not a blocker — see "Test strategy" follow-up item).
- Upstream (decision, resolved — see Decision log): existing/seeded users are provisioned with a random, unusable password hash and a `must_reset_password=true` flag by a one-time backend migration (AC4). Giving a specific user a real initial password is done via a companion operator-invoked provisioning script (AC5) — both are now in-scope for AUTH-02 itself; no separate story is needed and none is planned.
- Downstream: AUTH-01 (login screen UI) — consumes this story's login endpoint contract and generic error message. AUTH-04 (auth state management/persistence) — consumes the successful-login response shape (token/session) produced here.

## Test strategy

- **Stub interface**: tests are written against a fake credential verifier with the signature `verify_credentials(email: str, plaintext_password: str) -> bool`, matching the shape AUTH-03's real hash-and-verify function will expose (i.e. a single boolean-returning check, no plaintext persistence, no distinguishable timing/error signal between "no such email" and "wrong password"). The stub is seeded in test setup with a small fixture set: one user with a valid credential, one user with no credential provisioned, and one email with no matching user record at all.
- **AC1 (valid login)**: test calls the login endpoint with the fixture user's email and correct password against the stub; asserts a successful auth response per AUTH-04's shape and asserts the `users` table row count is unchanged (no insert, no duplicate).
- **AC2 (invalid login, generic error)**: two test cases — (a) email not present in the stub's fixture set, (b) email present but wrong password — both assert identical HTTP status (`401`) and identical response body (`"Invalid email or password."`), with no field-specific validation error distinguishing the two cases.
- **AC3 (existing user without credentials)**: test calls the login endpoint with the fixture user whose `must_reset_password` flag is `true` in the stub; asserts the same generic `401` response as AC2, and asserts no silent authentication occurs.
- **AC4 (provisioning migration)**: test seeds a fixture set of rows with and without a `password_hash`, runs the migration function directly (not via HTTP), and asserts every credential-less row now has a hash value (never equal to any fixed/hardcoded string, and different across rows) and `must_reset_password=true`; re-running the migration is asserted to be a no-op for rows already provisioned.
- **AC5 (provisioning script)**: test invokes the script's underlying function directly with a fixture email + password, asserts the row's `password_hash` changes to a value that verifies against the supplied password via the same `verify_credentials` stub interface, asserts `must_reset_password` is now `false`, and asserts the plaintext password never appears in any log capture or persisted field other than as an input to the hash function.
- **Follow-up (tracked, not a blocker)**: once AUTH-03 ships its real hash-and-verify implementation and schema migration, add a follow-up integration test that swaps the stub `verify_credentials` for the real implementation and re-runs the same AC1-AC5 test cases end-to-end against a real migrated `users` table, confirming parity with the stub-based results. This follow-up validates production behavior; it does not gate this story's own validation or `Independent test: true` status.
