### TC-09 judgment — ambiguity assessed, not a failure

PLAN.md's literal TC-09 wording says "the registered unauthorized handler fires." The shipped
test instead asserts the handler is **not** re-invoked, because AUTH-04's already-locked dedup
guard (`hadToken` check in `userApi.js`'s response interceptor) skips the handler once `logout()`
has already synchronously cleared the token before the delayed 401 arrives.

Assessment: this is the correct behavior, not a bug requiring escalation. Re-invoking the handler
a second time here would directly violate AUTH-04's own shipped and PASS-validated dedup guarantee
(`docs/features/AUTH-04/PLAN.md`, already merged as `a2ec706f`) — the entire point of that guard is
to prevent exactly this double-fire. The literal PLAN sentence describes the general race-condition
mechanism at a high level ("the same unauthorized handler" as the single code path, contrasted with
a hypothetical second/duplicate handler) rather than mandating a second literal invocation on every
delayed 401. The implementation-agent's interpretation is reasonable, was logged transparently in
`docs/features/AUTH-07/QUESTIONS.md`, and the shipped test verifies real, correct, non-throwing
behavior (rejection still propagates, no duplicate callback, no crash). No escalation needed;
verdict counted as PASS.
