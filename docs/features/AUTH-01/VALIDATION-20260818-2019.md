## Context for this round

This is a full regression re-validation of AUTH-01 now that the whole epic is merged. Since
AUTH-01 was first validated in isolation, three downstream changes landed on top of its files:

1. **AUTH-04** replaced AUTH-01's original in-memory `setAuthToken` (an axios-default-header-only
   setter, no persistence) with a `localStorage`-backed version in `frontend/src/services/userApi.js`.
2. **AUTH-05** mounted `LoginScreen` into `App.jsx`'s `isAuthenticated` gate (AUTH-01 had
   deliberately left it unmounted per its own PLAN), and — per its security-review fix — **deleted**
   `frontend/src/services/userAuthService.js` (AUTH-01's mocked login stub) and replaced it with a
   real backend call via `userApi.login()` hitting `POST /api/auth/login`.
3. **AUTH-07**'s validation added a `useRef`+`useEffect` focus-on-mount behavior to
   `LoginForm.jsx` (documented in AUTH-01's PLAN.md Addendum), moving keyboard focus to the email
   field on every mount.

All three changes were confirmed present and intact on disk. AUTH-01's automated test files
(`LoginForm.test.jsx`, `LoginScreen.test.jsx`) were found already updated to spy on
`userApi.login`/`userApi.setAuthToken` directly rather than the deleted `userAuthService` mock —
i.e. the implementation-agent that made AUTH-05's fix correctly updated AUTH-01's tests in place.
The TC **JSON narrative text** (`given`/`then` fields in `docs/test-cases/AUTH-01.json`), however,
still references "mocked `userAuthService.login`" in TC-02, TC-03, TC-04, TC-06, TC-07, TC-09 —
this is flagged below as a **stale-TC-wording** finding, not a functional failure: every one of
those TCs' actual assertions (call order, generic non-leaking error message, no password leak,
synchronous loading state, submit blocked on empty fields) still holds against the current merged
implementation, verified this round both via the Vitest suite and live against the real FastAPI
backend (see Stack smoke section).

**No genuine regression was found.** All 9 AUTH-01 TCs pass against the current merged codebase.

### AUTH-01-TC-02, TC-03, TC-04, TC-06, TC-07, TC-09 — stale "userAuthService" wording

- These 6 TCs' `given`/`when`/`then` narrative text in `docs/test-cases/AUTH-01.json` refers to
  "a mocked `userAuthService.login`" — that module was deleted by AUTH-05.
- **Assessed against current behavior, not silently passed:** for each, the underlying assertion
  (call-order, generic error text, no-password-leak, empty-field block, synchronous loading state)
  was checked against the current implementation and test file, and holds true. The test files
  themselves (`LoginForm.test.jsx`, `LoginScreen.test.jsx`) were already correctly updated to spy
  on `userApi.login`/`userApi.setAuthToken` in place of the deleted mock — this happened as part
  of AUTH-05's fix, not this validation round.
- **Recommendation:** reword the 6 TC JSON entries' `given`/`then` text to say `userApi.login`
  instead of `userAuthService.login` in a future TC-authoring pass, so the manifest stops
  describing a module that no longer exists. This is a documentation-debt item, not a functional
  gap — logged here rather than silently corrected, per this round's explicit request to flag
  (not silently pass) stale TCs.

### AUTH-01-TC-02 — persistence-mechanism wording also stale

- TC-02's `then` clause says `userApi.setAuthToken is called with the token` without specifying
  the persistence mechanism — this wording still holds unchanged (the TC never asserted the old
  in-memory-only behavior explicitly), so no reword needed here beyond the `userAuthService`
  point above. Confirmed `setAuthToken` now persists to `localStorage` (AUTH-04) and the call-site
  contract (`login → setAuthToken → onLoginSuccess`, in order) is unchanged and still enforced by
  `LoginScreen.test.jsx`.
