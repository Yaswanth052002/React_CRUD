### Failed (bug blocks)

### AUTH-01-TC-05 — Login form reflows without horizontal scroll at 320px viewport width (Priority: Must)

- AC: form remains fully usable with no horizontal scrolling at 320px viewport width.
- Attempts: 2 (both FAIL — confirmed not a flake, a structural defect in the test itself)
- Steps executed:
  1. Render `LoginForm` in jsdom.
  2. Set `window.innerWidth = 320` and dispatch a `resize` event.
  3. Assert `form.scrollWidth <= (form.clientWidth || form.scrollWidth)`.
- Expected: a genuine layout assertion that would fail if the form overflowed horizontally at 320px.
- Actual: jsdom has no real layout engine — `form.scrollWidth` and `form.clientWidth` are both `0` for every element regardless of CSS or viewport width (independently confirmed via a scratch probe: `scrollWidth 0 clientWidth 0`). The assertion `0 <= (0 || 0)` → `0 <= 0` is true unconditionally. This test would pass even if the component's CSS were deleted entirely or a fixed 900px-wide element were added.
- Failure reason: tautological/vacuous assertion — provides zero real verification of AUTH-01-FR-2's 320px reflow requirement, despite showing green in `npm run test`.
- Likely cause: jsdom cannot compute real layout; a proper check needs either (a) a headless-browser runner (Playwright, per PLAN.md's own acknowledgment that a real e2e runner is deferred to a future story), or (b) a CSS-rule-presence assertion (e.g. assert the panel/media-query rule exists and applies a `max-width`/`flex-wrap` at ≤320px) instead of computed pixel geometry, which jsdom can support meaningfully.
- Action: PLAN.md explicitly defers real-browser/viewport E2E to manual QA and a future e2e-runner story; this finding does not block the story's documented scope decision, but the automated TC-05 as currently written should not be relied on as behavioral proof and should either be rewritten to assert something jsdom can actually verify, or reclassified/removed with the gap tracked as a carry-forward.
