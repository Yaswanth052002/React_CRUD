### F-004 — Mocked `userAuthService.login()` accepts any non-empty credential pair

- Source: checklist/auth
- Severity: Medium
- File: `frontend/src/services/userAuthService.js:14`
- Issue: The mock resolves successfully for *any* non-empty `email`/`password` combination
  (no real credential check, by design — the module's own header comment states
  `AUTH-02 owns replacing this with a real backend call`). If this mock ever shipped unreplaced
  behind a mounted `LoginScreen`, it would function as a universal auth bypass.
- Mitigating factors verified this review:
  - `LoginScreen`/`LoginForm`/`userAuthService` are not imported anywhere in `App.jsx` or
    `main.jsx` (`grep` confirmed zero references) — dead code from the running app's
    perspective for this story.
  - `npm run build` output (`frontend/dist/assets/index-*.js`) does not contain the mock's
    `mock-token-` template string or the `Invalid email or password...` UI string — confirmed
    via grep against the built bundle, i.e. Vite's tree-shaking excludes the unreferenced
    module graph from the production artifact for this story.
  - Ownership of the mock's replacement is explicitly tracked (AUTH-02) and is not silently
    dropped.
- Fix / action: no code change required for AUTH-01 to merge; ensure AUTH-02 (or whichever
  story wires `LoginScreen` into `App.jsx`) is gated on replacing `userAuthService.login` with
  the real backend call before that mount lands — track this dependency explicitly (it is
  already implied by the module's own header comment, but is not yet a tracked
  `pending_carry_forward` item in `state.json`).

## Manual OWASP checklist + stack-pattern pass detail

**Input.** `LoginForm.jsx` validates email format (regex) and non-empty password client-side
before calling `onSubmit`; `noValidate` on the `<form>` is intentional (custom validation UI,
not a bypass — inputs are still constrained by `type="email"`/`type="password"`). No
string-built queries, no `eval`, no shell concatenation anywhere in the diff (SAST grep pass,
0 hits — see below).

**Auth / authorization.** Password field `autoComplete="current-password"`, email field
`autoComplete="username"` — correct semantic hints, no `autoComplete="off"` anti-pattern.
`setAuthToken` (`userApi.js:101-103`) only accepts a token string and assigns it to
`client.defaults.headers.common.Authorization` — it does not accept an arbitrary header name
or value object, so it does not introduce a header-injection surface. Token storage is
in-memory only (axios instance default, not `localStorage`/`sessionStorage`/cookie) — no XSS
persistence-at-rest surface added by this diff; this is a known, already-tracked
non-security "risk" item in `state.json.pending_carry_forward`
(`R-01-userApi-setAuthToken-collision`, kind=`risk` not kind=`finding` — AUTH-04 already
implements the authoritative `localStorage`-backed version and this collision is an expected,
mechanical merge-order resolution per that story's ADR-3, not a security defect in AUTH-01's
code as delivered).

**Generic error message (AC2-equivalent).** `LoginScreen.jsx` hardcodes a single
`GENERIC_AUTH_ERROR` string (`"Invalid email or password. Please try again."`) shown on *any*
rejection from `login()`, regardless of the underlying rejection reason — confirmed the mock
itself (`userAuthService.js`) also never distinguishes invalid-email from invalid-password
(single `reject(new Error("Invalid credentials"))` branch for any falsy email or password) and
this inner message is never surfaced to the UI (only the outer generic string is). No timing
side-channel: the mock always waits the same fixed `300ms` via `setTimeout` regardless of
whether email/password are valid, non-empty, or empty — success and failure paths share the
identical delay.

**Data / PII.** Password value lives only in `LoginForm`'s local `useState` (`values.password`)
and is never logged (`console.log`/`console.error`/`print` grep across the diff: 0 hits
matching `email|password|token|ssn|phone`) or sent anywhere except as a plain function argument
to `onSubmit`/`login(email, password)`. The component is not persisted across
mount/unmount (no `localStorage`/`sessionStorage` write of form values found), and unmounting
via React's normal lifecycle (e.g. after `LoginScreen`'s `onLoginSuccess` swaps views, once a
future story mounts it) discards the state. `LoginForm.test.jsx` TC-07 independently exercises
this (asserts `wrong-password` never appears in `document.body.textContent` or any
`console.log`/`console.error` call after a rejected submit) — reviewed and consistent with the
static analysis above.

**Crypto.** No production crypto code touched. The mock's `mock-token-${Date.now()}` is
explicitly a placeholder value (not a real credential/session token — never leaves the browser,
never validated against anything server-side because there is no server-side auth yet); flagged
under F-004's mitigations rather than as its own weak-crypto finding, since it's mock-only, not
a real token-generation mechanism.

**Dependencies.** Covered by the deps-scan section above. Testing Library additions
(`@testing-library/react@16.3.2`, `@testing-library/jest-dom@7.0.1`, `@testing-library/dom@10.4.1`)
themselves: 0 audit findings; dev-only, never bundled into `frontend/dist` (confirmed via
`npm run build` + grep of build output).

**Errors.** No stack traces or internal identifiers are ever rendered to the user — the only
user-facing string from this flow is the fixed `GENERIC_AUTH_ERROR` constant.

**Stack pattern (react-patterns).** `LoginForm` (component) does not import `services/` directly
— it receives `onSubmit` via props from `LoginScreen` (page/container), matching the
`components/` vs `pages/`-equivalent layering convention already used by `Dashboard.jsx`/
`Users.jsx` (`components/` may not import `services/` directly). `LoginScreen` is the only layer
calling `userAuthService.login` and `userApi.setAuthToken`, consistent with "services/ is the
only layer allowed to call the backend." No direct `axios` import outside `userApi.js` anywhere
in the diff (grep confirmed).
