## Failed (bug blocks)

### LIVE-01 — `GET /api/auth/me` does not exist on the real backend (Priority: Must — blocks all of AUTH-06-FR-1)

- Requested check: create a real user via `POST /api/users`, log in via `POST /api/auth/login`,
  call `GET /api/auth/me` with the real bearer token, confirm response is exactly `{name, email}`.
- Steps executed:
  1. `POST /api/users` with a fresh user + password → `200`, user created (id 6).
  2. `POST /api/auth/login` with that user's credentials → `200`, valid 3-part JWT returned
     (`sub`=email, `exp`≈+60min — correct per AUTH-02's contract).
  3. `GET /api/auth/me` with `Authorization: Bearer <token>` → **`404 {"detail":"Not Found"}`**.
- Expected: `200 {"name": "...", "email": "..."}`.
- Actual: `404 Not Found` — no route matches `/api/auth/me` in `backend/app/api/auth.py`
  (only `POST /api/auth/login` is registered) or anywhere else in `backend/app/api/`.
- Root cause trace: `docs/features/AUTH-06/REQUIREMENTS.md` explicitly places the
  `GET /api/auth/me` backend endpoint "Out" of AUTH-06's scope, attributing it to
  "AUTH-04/AUTH-02's implementation". `docs/features/AUTH-04/PLAN.md` only adds **frontend**
  auth-token plumbing (`userApi.js` interceptors, `App.jsx` state) — it never adds a backend
  route. `docs/features/AUTH-02/PLAN.md`'s file table (F-01..F-14) only builds
  `POST /api/auth/login` plus provisioning — no `/me` route. No PLAN.md in the epic actually
  owns implementing this endpoint; it fell into a gap between AUTH-02, AUTH-04, and AUTH-06.
  `backend/tests/test_auth.py` (57 passing tests) has no coverage for `/me` either, so no test
  suite caught the gap.
- Impact: `Settings.jsx` (AUTH-06) is unusable end-to-end in the real system — every real user
  visiting Settings gets the persistent error banner (TC-08's failure path, ironically the
  "success" case for that TC but the failure case for the feature). `userApi.getCurrentUser()`
  always throws in production.
- Artefact: n/a (manual curl reproduction; not a scripted TC — the existing TC suite mocks the
  HTTP boundary per PLAN.md T-04/condition C-10, so no automated TC currently detects this).
- Action: file this as a new backend task (owner: AUTH-02 or AUTH-04, whichever team accepts the
  file-table slot) to add `GET /api/auth/me` — service-layer derives identity from the JWT
  `sub` claim (already present, no schema change needed), returns `{name, email}` via a new
  `schemas/auth.py` response model, mirroring the layering rule (`api → service → repository`).
  Recommend adding a regression-tagged TC (`regression-AUTH-06-TC-01`) once fixed, per the
  regression-tag protocol, plus a `backend/tests/test_auth.py` case for the new route.
