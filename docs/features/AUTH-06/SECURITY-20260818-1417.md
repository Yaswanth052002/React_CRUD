## Manual OWASP checklist + stack-pattern pass

### 1. `getCurrentUser()` — identity source and error normalization
- Confirmed: `getCurrentUser()` takes no arguments and is called with no arguments (also
  asserted by `Settings.test.jsx` TC-10: `expect(userApi.getCurrentUser).toHaveBeenCalledWith()`).
  It sends no client-supplied identity parameter — the request is a bare `GET /api/auth/me`;
  the request interceptor attaches `Authorization: Bearer <token>` from `getStoredToken()`, so
  identity resolution is entirely server-side from the bearer token. Matches
  `security-baseline.md` "authenticated routes ... user-context check" intent for the client
  side of this contract (server-side `/api/auth/me` handler is AUTH-05/backend scope, not
  touched by this diff).
- Failures flow through the existing `normalizeError()` (unchanged by this story), which strips
  axios/HTTP internals down to a `detail` string or a small set of generic messages — no stack
  trace, no raw Axios error object, ever reaches `Settings.jsx`. `Settings.jsx` renders only
  `err.message` from the normalized `Error`. No gap found.

### 2. `Settings.jsx` — field scoping / over-rendering / logging
- Rendered fields are exactly `currentUser.name` and `currentUser.email` (lines 63, 67) — no
  other field of the resolved object is read or interpolated anywhere in the component. Verified
  against `Settings.test.jsx` TC-03, which mocks a response including `role: "Admin"` and
  `id: 42` and asserts neither value appears in the rendered DOM. No over-fetching/over-rendering
  risk: even if the backend response includes extra fields, they are inert.
  the diff itself confirms.
- No `console.log`/`console.error`/`console.warn` call exists anywhere in `Settings.jsx`. Grep
  confirms zero matches for `console\.` in the file. `Settings.test.jsx` TC-11 independently
  spies on `console.log`/`console.error` across both the success and failure render paths and
  asserts the captured output contains neither the name nor the email string. No PII-in-logs
  risk from this component.

### 3. `handleLogout()` — call graph
- `handleLogout()` (lines 23-26) contains exactly two statements: `userApi.logout()` then
  `onLogout()`. No navigation call (`window.location`, `history.push`, etc.), no additional
  state mutation, no side effect beyond what the two delegated calls perform. Confirmed by
  static read of the 4-line function body and corroborated by `Settings.test.jsx` TC-04 (call
  order) and TC-05 (`window.location.href` unchanged after the click). This satisfies the "no
  additional side effect" check from the task brief — `logout()`'s own internal behavior
  (client-side-only token clear, no server call) is AUTH-07's export and out of this review's
  scope, but the call boundary from AUTH-06's side is clean.

### 4. No `isAuthenticated` prop / no eager-fetch bypass path
- `Settings`'s function signature is `Settings({ onMenuClick, onLogout })` — no
  `isAuthenticated` parameter is declared, destructured, or referenced anywhere in the file.
  `Settings.test.jsx` TC-06 asserts identical render output whether or not a stray
  `isAuthenticated={true}` prop is passed, confirming the component cannot be influenced by
  (and does not depend on) that prop.
- The component's `useEffect` fires unconditionally on mount and calls `getCurrentUser()`
  regardless of any auth flag — but this is not a new bypass path: `App.jsx`'s unmodified
  gating (AUTH-05 scope, untouched by this diff — confirmed by the `App.jsx` diff hunk, which
  only swaps `SettingsPlaceholder` for `Settings` inside the existing
  `activeView === "settings"` branch of the already-gated authenticated view tree) is the sole
  route to mounting `Settings` at all. There is no second `<Settings />` usage, lazy route, or
  export path introduced by this diff that would let it mount pre-authentication. If the token
  is absent/expired, `getCurrentUser()` simply fails and `normalizeError()` surfaces a readable
  error banner — no raw data leaks, no crash, no privileged rendering. No finding.

### 5. Unstyled `.banner-error` — confirmed cosmetic, not information disclosure
- Already disclosed as LOW in `docs/features/AUTH-06/REVIEW.md` F-1 (missing `.banner`/
  `.banner-error` CSS rule in `frontend/src/styles/index.css`, which is outside AUTH-06's file
  table). Re-checked from a security angle specifically: the text rendered inside that banner is
  always `error`, which is set from `err.message` — i.e. exactly and only what
  `normalizeError()` in `userApi.js` already produces (a fixed set of generic strings, or the
  backend's already-sanitized `detail` field per the FastAPI layering contract in
  `fastapi-patterns` § Error handling, which forbids raw stack traces/exception text reaching
  the client). `Settings.jsx` performs no additional string concatenation, header inspection, or
  raw-error passthrough beyond consuming `err.message`. Confirmed: this is purely a missing-CSS
  /accessibility-contrast issue (no color/style distinguishing the error state), not an
  information-disclosure defect. No change to severity or category from the code review's
  classification.
