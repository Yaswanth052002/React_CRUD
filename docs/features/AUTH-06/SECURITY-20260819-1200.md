## Manual OWASP checklist — targeted at the new endpoint

### JWT validation (deep-dive per reviewer instructions)

Read `backend/app/services/auth_service.py` in full (not just the diff) to confirm the algorithm allowlist is real, not just locally consistent:

- `_JWT_ALGORITHM = "HS256"` (line 50) is a single module-level constant used for **both** `jwt.encode(..., algorithm=_JWT_ALGORITHM)` at issuance (line 198) and `jwt.decode(token, secret, algorithms=[_JWT_ALGORITHM])` at verification (line 221, the new `get_current_user_from_token`).
- `algorithms=` is an explicit single-element allowlist, not omitted — PyJWT cannot fall back to `alg: none` or an attacker-chosen algorithm (PyJWT rejects `alg: none` unless `algorithms=["none"]` is explicitly passed, which it is not here).
- No `options={"verify_exp": False}`, `options={"verify_signature": False}`, or any `options=` override is passed to `jwt.decode` — PyJWT's default behavior (verify signature, verify `exp` if present) is in force. Signature is genuinely verified against `os.getenv("JWT_SECRET_KEY")`, not merely decoded/parsed with `jwt.decode(token, options={"verify_signature": False})` (that anti-pattern is absent).
- Missing-secret case (`if not secret: raise unauthorized`) fails closed rather than falling back to a default/empty secret — confirmed no `secret = os.getenv("JWT_SECRET_KEY", "<default>")` pattern.

**No finding.** Verified correct, not just claimed correct by the implementation summary.

### IDOR / BOLA

`get_current_user_from_token` takes only `token: str`; `email = payload.get("sub")` is the **sole** source of identity, then `self.repo.get_by_email(email)` loads the row that becomes the response. The route signature is `def me(current_user: User = Depends(get_current_user))` — no query param, path param, or request body is accepted on `GET /api/auth/me` at all, so there is no parameter surface through which a caller could supply or override an identity distinct from the token's `sub`. `CurrentUserResponse` echoes back only `name`/`email` taken from the resolved `current_user` object, not from any request-supplied value.

**No finding.**

### Timing / enumeration (401 uniformity)

Read `get_current_user_from_token` directly rather than trusting the docstring: a single `unauthorized = HTTPException(401, "Could not validate credentials.")` object is constructed once at the top of the method and the exact same object is `raise`d on every failure branch — missing secret, `jwt.PyJWTError` (covers invalid signature, expired, malformed), missing `sub` claim, and unknown user (`get_by_email` returns `None`). All four branches produce byte-identical status code and body. The router's `get_current_user` dependency also raises the same literal message/status for a missing Authorization header (`credentials is None` branch in `backend/app/api/auth.py`), so "no token" and "bad token" and "token for a user that doesn't exist" are all indistinguishable to the caller. Confirmed by test `test_me_without_a_token_is_rejected` and `test_me_with_an_invalid_token_returns_generic_401`, both asserting the identical `{"detail": "Could not validate credentials."}` body.

**No finding.** (Response-time side channel from the extra DB lookup on the "unknown user" path vs. the fail-fast paths (missing secret/malformed token) is a theoretical timing difference, but this is an internal admin tool with no untrusted external population probing for account enumeration; not flagged as a risk requiring mitigation under the active standard profile.)

### Token leakage in logs/errors

No `logger.*` or `print(...)` call was added anywhere in `get_current_user_from_token`, `get_current_user`, or the `me` route handler — the diff introduces zero new logging statements. The three `except Exception:` blocks in `auth_service.py` (lines 118, 138, 199) are all pre-existing, unrelated to this endpoint (password-hashing and JWT-encode-at-login paths), and none of them interpolates `str(exception)` into a response or log message — confirmed by inspection, no behavior change from this diff. The new code path uses `except jwt.PyJWTError:` (narrow, not bare `except Exception`) and discards the exception entirely, re-raising the pre-built generic `unauthorized` object — the raw exception object/message (which could contain token fragments in some PyJWT error strings) is never touched, logged, or serialized.

**No finding.**

### Rate limiting / DoS exposure on an unauthenticated-reachable endpoint

`GET /api/auth/me` requires a bearer token to succeed, but any caller — including one with no valid credentials — can hit the endpoint and receive a fast, cheap 401. Unlike `POST /api/auth/login` (which has `_check_rate_limit`/`_record_failed_attempt` keyed by a hashed email, see `auth_service.py` lines 157-180), the new endpoint applies no throttling of any kind: an attacker can send an unbounded stream of `Authorization: Bearer <garbage>` requests with no backoff.

Assessed risk: `jwt.decode` failure is cheap (no DB hit on the invalid-signature/expired/malformed paths — the `get_by_email` query only runs after a token successfully verifies), so this is not an amplification vector, and there is no per-user lockout state to grief (nothing here can lock out a legitimate user the way a login-attempt-counter endpoint could). Successful brute-force of a valid JWT via this endpoint is cryptographically infeasible (HS256 signature forgery, not a guessable secret exposed elsewhere in this diff). Given the declared governance profile — "generic internal admin tool — no regulated domain" (CLAUDE.md § Target platforms) — and the absence of a rate-limiting convention applied elsewhere in the codebase for read-only authenticated endpoints (only the login/credential-guessing surface is throttled), this is accepted as low-risk for the current profile rather than a blocking gap.

**Finding (Low, non-blocking):** `GET /api/auth/me` has no request throttling, unlike `/api/auth/login`. Track as backlog hardening if this API is ever exposed beyond the internal admin tool's current trust boundary (e.g. before adding a public-facing client or a regulated-data profile).

### response_model / sensitive-field exposure (fastapi-patterns stack check)

`response_model=CurrentUserResponse` on the route, and `CurrentUserResponse` only declares `name: str` / `email: str` — `id`, `role`, `status`, `phone`, and `password_hash` (or any hash field) on the `User` ORM model are structurally unreachable through this endpoint regardless of what `current_user` carries, per FastAPI's `response_model` filtering plus the schema not declaring those fields. Matches the fastapi-patterns convention ("response_model strips sensitive fields") and the stated design intent in the schema's own docstring.

**No finding.**

### Layering (fastapi-patterns)

`api/auth.py` → `AuthService` → `UserRepository.get_by_email` — no layer is skipped; the router does not touch SQLAlchemy directly. `get_current_user` (the `Depends()` chain) lives in the router module as a dependency function, consistent with FastAPI idiom, and delegates all decode/verify/lookup logic to the service layer.

**No finding.**
