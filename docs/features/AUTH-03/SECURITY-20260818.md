## Manual OWASP checklist + stack-pattern pass

### A02:2021 — Cryptographic Failures

- **No homegrown crypto.** `hash_password`/`verify_credentials` delegate entirely to
  `passlib.context.CryptContext(schemes=["bcrypt"], ...)` — no custom hash/compare logic
  remains (the AUTH-02 `hashlib.pbkdf2_hmac` + `hmac.compare_digest` placeholder is fully
  removed, not left as a parallel path). Verified via `git diff`: `_hash_password`/
  `_verify_password`'s bodies are gone; `_hash_password` is now a one-line alias to the new
  public `hash_password`.
- **Modern primitive, adequate work factor.** `bcrypt__rounds=12` is within the
  OWASP-recommended range (≥10, typically 10–14) for an interactively-verified login path;
  matches `.claude/rules/security-baseline.md`'s "passwords stored via argon2id/bcrypt".
- **No downgrade path.** `CryptContext(schemes=["bcrypt"], ...)` registers exactly one scheme.
  Verified interactively: `ctx.schemes() == ('bcrypt',)`, `ctx.default_scheme() == "bcrypt"`.
  `deprecated="auto"` is inert with a single-scheme context (nothing to mark deprecated against).
  There is no code path — configuration or call site — that would accept or verify a
  weaker scheme than bcrypt. The only "other format" the verify path recognizes is AUTH-02's
  now-foreign `salt$hex_digest` placeholder rows, which raise `passlib.exc.UnknownHashError`
  and are explicitly caught to return `False` (reject cleanly, not a partial/weak-verify
  acceptance) — this is the intentional, documented AUTH-02→AUTH-03 migration boundary, not a
  downgrade oracle. No finding.
- **No plaintext password persistence.** Grepped the full diff for `password` usage: every
  sink is either (a) `_pwd_context.hash(plaintext)` (produces only the salted bcrypt digest,
  never the plaintext, for storage), (b) a local `plaintext`/`plaintext_password` parameter that
  is popped from the request payload and passed straight into `hash_password` in
  `user_service.create_user` (never assigned to `data` alongside `password_hash`, so it cannot
  reach `repo.create`), or (c) test-fixture literals. The two `except Exception` blocks in
  `auth_service.py` (`hash_password`, `verify_credentials`) log only a static string or
  `extra={"user_id": ...}` — no plaintext, no email, no hash value. `PasswordHashingError`'s
  message is a static, generic string, never interpolates the plaintext. Confirmed by
  `test_password_hashing.py`'s own assertions (`"some-plaintext-password" not in
  record.getMessage()`, not in the raised exception's `str()`). No finding.
- **Minor, non-blocking observation (Low):** `UserCreate.password_min_length` enforces a floor
  (≥8 chars) but no ceiling. bcrypt silently truncates input at 72 bytes (a well-known
  algorithm property, not a passlib/bcrypt bug) — a password longer than 72 bytes hashes
  identically to its first-72-byte prefix, silently reducing effective entropy for very long
  inputs. Low risk for this admin-tool threat model (no untrusted self-signup; accounts are
  operator-provisioned per AUTH-02's AC4/AC5), not a Critical/High per the checklist's
  "modern primitives only" bar (bcrypt itself is still a modern, approved primitive) — recorded
  as a Low finding rather than blocking. See F-C01 below.

### F-C01 — No maximum length on `UserCreate.password`

- Source: `checklist/crypto`
- Severity: Low
- File: `backend/app/schemas/user.py:49-54`
- Issue: `password_min_length` validates a floor (≥8) only; bcrypt truncates at 72 bytes, so
  passwords beyond that length silently lose effective entropy on truncation.
- Fix: add a reasonable max-length check (e.g. reject/normalize passwords over 72 bytes) in the
  same validator, or document the bcrypt 72-byte behavior explicitly if intentionally accepted.
- Not blocking: standard-profile, non-regulated, operator-provisioned accounts; low exploitability.

## Assessment of REVIEW.md's known MEDIUM finding (F-1: private `_pwd_context` import)

`backend/tests/test_password_hashing.py:16` imports the module-private `_pwd_context` symbol to
monkeypatch its `hash`/`verify` methods and force an otherwise-untriggerable library-failure
path (TC-05). Security assessment of this specific finding, as requested:

- **No security implication.** The import is test-only code, never shipped/executed in the
  production path, and does not change `_pwd_context`'s runtime configuration (`schemes`,
  `rounds`) or expose it to any non-test caller. It does not create a way for
  production/request-handling code to bypass bcrypt or substitute a weaker scheme — the
  monkeypatch is scoped to the test function's lifetime (via `monkeypatch`, which auto-reverts).
- It is purely a **testability/coupling** concern (test white-boxes an implementation detail,
  so a future rename/refactor of `_pwd_context` breaks the test even though the public
  `hash_password`/`verify_credentials` contract is unchanged) — already correctly categorized as
  MEDIUM under `reusability-baseline.md` in `docs/features/AUTH-03/REVIEW.md` (F-1), not a
  security category. Not re-flagged here to avoid double-counting; confirmed no security
  reclassification is warranted.
