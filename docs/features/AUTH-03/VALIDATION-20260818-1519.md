### Live regression checks (beyond the JSON TC set, per explicit validation instruction)

1. **Bcrypt hashing confirmed live, not just in pytest.** `POST /api/users` against the real
   running server with `password: "CorrectHorse123"` persisted `password_hash` as
   `$2b$12$Z4kTBNB0W5ksUdXI7/CKhurOBqUTTsLNfjmEPMmKhUG9n9dVYDvAa` (verified via direct sqlite
   read of `backend/users.db`) — a real bcrypt hash (`$2b$12$` prefix, work factor 12), distinct
   from the plaintext, and distinct in form from AUTH-02's old `salt$hex_digest` `pbkdf2_hmac`
   placeholder. No overwrite/regression of the hashing algorithm found post-merge.
2. **Genuine regression found: freshly-created users cannot log in with the correct password.**
   See bug block below.
3. Confirmed the underlying bcrypt verify + AUTH-02's JWT-signing amendment both work correctly
   in isolation: after manually clearing `must_reset_password` via
   `AuthService.set_user_initial_password(...)` (AUTH-02's AC5 provisioning helper), login with
   the same correct password against the same user succeeded and returned a valid signed JWT.
   This isolates the regression to `UserService.create_user`, not to `verify_credentials`,
   `hash_password`, or JWT issuance.

### Failed (bug blocks)

### REGRESSION-01 — POST /api/users does not clear `must_reset_password`; freshly-created users can never log in

- Severity: High (blocks the story's own stated acceptance behavior — "login against a
  freshly-created user succeeds with the correct password")
- Not tied to an existing TC id in `docs/test-cases/AUTH-03.json` — this is a coverage gap: no
  TC in the manifest exercises "create via `POST /api/users`, then log in with that password."
  TC-01 only asserts the hash shape; TC-03/TC-04 call `AuthService.verify_credentials` directly
  against a manually-seeded row where `test_auth.py`'s fixture sets `must_reset_password=False`
  by hand (`tests/test_auth.py` line ~47) — bypassing the real `create_user` code path.
- Steps executed (live, against the running FastAPI dev server, not mocked):
  1. `POST /api/users` with a full valid payload including `"password": "CorrectHorse123"`.
     Response: `201`-equivalent success body, no `password`/`password_hash` leaked (TC-08
     assertion holds).
  2. Direct sqlite read of `backend/users.db`: `password_hash` is a valid, correctly-salted
     bcrypt hash; `must_reset_password = 1` (True).
  3. `POST /api/auth/login` with the same email and the exact same plaintext password
     `"CorrectHorse123"`.
- Expected: `200 { "token": "<jwt>" }` (per AUTH-03's own scope note in README §11a and the
  task's explicit ask: "login against a freshly-created user succeeds with the correct
  password").
- Actual: `401 {"detail": "Invalid email or password."}` — the same generic failure returned for
  a wrong password.
- Failure reason: `AuthService._verify_credentials` unconditionally returns `False` when
  `user.must_reset_password` is `True` (by design, per AUTH-02's ADR — an "unprovisioned"
  account). `UserService.create_user` (AUTH-03's `F-03`/T-04) sets `password_hash` via
  `AuthService.hash_password` but never clears `must_reset_password`, and the ORM column
  defaults to `True` (`backend/app/models/user.py:37`). Every user created through the CRUD
  dashboard's "+ Add User" flow is therefore permanently stuck as "must reset" and can never log
  in with the password they were given at creation time, without an operator separately running
  AUTH-02's AC5 `set_initial_password.py` script for every single new user.
- Root cause is isolated to `backend/app/services/user_service.py::create_user` (does not touch
  `must_reset_password`), not to bcrypt hashing/verification or JWT issuance (both independently
  confirmed correct — see live check #3 above).
- Likely cause: AUTH-03's `PLAN.md` §2 `F-03` row and §3 module hierarchy never mention
  `must_reset_password` — this is a scope gap in the original PLAN, not code that regressed
  during the AUTH-02/AUTH-08 merges. It surfaces now because this is the first regression pass
  that exercises the real end-to-end "create then log in" path instead of directly seeding rows
  with `must_reset_password=False` in test fixtures.
- Suggested fix: `UserService.create_user` should set `must_reset_password=False` when a
  `password` is supplied at creation time (an admin-set password on creation should be
  immediately usable). Add a regression-tagged TC (e.g. `AUTH-03-TC-13`,
  `tags: ["regression-REGRESSION-01"]`) asserting `POST /api/users` → `POST /api/auth/login`
  round-trip succeeds with the same password, per the regression-tag protocol.
- Artefact: live curl transcript captured in this validation run (server log
  `tmp/smoke-fastapi.log`, since cleaned up per PASS-smoke retention rule — smoke itself passed;
  this finding was captured via manual flow calls after smoke, not a smoke failure).
