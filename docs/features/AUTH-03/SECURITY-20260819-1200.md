## Manual OWASP checklist + stack-pattern pass

### A07:2021 — Identification and Authentication Failures (primary focus)

- **Confirmed this does not create a provisioning-gate bypass.** Read
  `backend/app/services/auth_service.py` in full: the credential-less migration path
  (`provision_existing_users_with_random_password`, lines 77-90) is untouched by this diff — it
  still sets `password_hash` to a cryptographically random, never-provisioned-to-anyone hash
  **and** `must_reset_password: True` for every row with `password_hash IS NULL`. The fixed
  `create_user()` path and this migration path are structurally disjoint: `create_user()` only
  reaches `data["must_reset_password"] = False` after `AuthService(self.db).hash_password(plaintext_password)`
  has *already succeeded* against a real, client-supplied plaintext password inside the same
  `try` block — if hashing fails, `PasswordHashingError` is raised and the flag assignment is
  never reached, so there is no path to a `must_reset_password=False` row without a real
  successful hash of a real password. This exactly mirrors the pre-existing, already-reviewed
  pattern at `AuthService.set_user_initial_password` (line 104: `{"password_hash": ...,
  "must_reset_password": False}` in one atomic update) — the fix brings `create_user()` into
  line with an established, reviewed convention rather than introducing a new one.
- **Confirmed no weakening of access control.** `_verify_credentials` (line 150) still gates on
  `must_reset_password` before delegating to the constant-time bcrypt `verify_credentials`
  check; that gating logic itself is unchanged by this diff (0 lines touched in
  `auth_service.py` for this commit range). The fix only changes whether a legitimately-created
  user's *own* correct password is accepted — it does not change what happens for a wrong
  password, an unknown email, rate limiting (`_check_rate_limit`/`_record_failed_attempt`,
  unchanged), or the indistinguishable `INVALID_CREDENTIALS_MESSAGE` (unchanged). An attacker
  who does not know the real password gains nothing from this change; there is no new way to
  authenticate as a user without their password.
- **No account-enumeration or timing regression.** No new branch, no new response-shape
  distinction, and no new log statement was added to any auth-facing code path in this diff.
- No finding.
