### Regression fix — live end-to-end repro against the real running server (not TestClient)

This repeats round 1's exact repro steps, live, to prove the fix against the actually-running
app:

1. `POST http://127.0.0.1:8000/api/users` with a full valid payload including
   `"password": "CorrectHorse123"` → `201`, response body `{"id":6, "email":"live.repro.round2@example.com", ...}` — no `password`/`password_hash` leaked (TC-08 assertion still holds).
2. Direct sqlite read of `backend/users.db` immediately after: `password_hash =
   $2b$12$OJx4DHjDDGsvLUuEuEvifO8t0bHFf4SappXvjRELafHqps5BXwltC` (valid bcrypt hash, work factor
   12) and **`must_reset_password = 0` (False)** — this is the exact column that was stuck at
   `1` (True) in round 1's repro.
3. `POST http://127.0.0.1:8000/api/auth/login` with the same email and the exact same plaintext
   `"CorrectHorse123"` → **`200 {"token": "eyJhbGci..."}`** — login succeeds on the first attempt
   with the creation password. Round 1 returned `401 {"detail":"Invalid email or password."}` at
   this exact step.
4. Negative control (unchanged behavior check): same user, wrong password
   `"WrongPassword999"` → `401 {"detail":"Invalid email or password."}` — confirms the fix does
   not weaken credential checking; only the true-positive path (correct password, freshly
   created account) was broken and is now fixed.

**Regression genuinely closed.** The fix is exactly the one-line change described
(`data["must_reset_password"] = False` in `UserService.create_user`, gated on successful
hashing) — confirmed via `git diff --stat` showing a single `+1` line in
`backend/app/services/user_service.py` relative to the pre-fix commit `4872e32e`, i.e. no other
behavior in `create_user` changed.
