## Manual OWASP checklist + stack-pattern pass

**Authentication and authorization**
- Client-side JWT handling is decode-only (`jwt-decode`), never signature verification — correct and intentional per AUTH-02's contract: the server verifies the signature on every API call; the client only reads `exp` for UX-level session-state (`App.jsx` `isTokenValid`). No client-side trust decision is made on a signature the client cannot verify.
- Decoded payload is used for exactly one field: `exp` (`frontend/src/App.jsx:19-20`). No `role`/`sub`/other claim is read client-side to gate UI, routing, or feature visibility — confirmed by reading the full diff hunk in `App.jsx`; the only consumer of `jwtDecode()`'s return value destructures `{ exp }`. This matches AUTH-02's payload contract (`sub` + `exp` only) and avoids the classic "trust the JWT payload for authorization" anti-pattern.
- Malformed/undecodable tokens are caught (`try/catch` in `isTokenValid`) and treated identically to "no token" — no uncaught exception, no fail-open path.
- `userApi.js` request interceptor attaches `Authorization: Bearer <token>` only when `getStoredToken()` returns non-null (`frontend/src/services/userApi.js:60-66`); no empty/`Bearer null` header is ever sent. The interceptor is registered once on the shared `client` and applies uniformly to all outgoing requests through that client (`get/post/put/delete`) — there is no separate unauthenticated request path in this module that could accidentally receive the header or exclude it inconsistently.
- Response interceptor's dedup guard (`frontend/src/services/userApi.js:73-86`): on a 401, it reads `hadToken = Boolean(getStoredToken())` **before** calling `clearAuthToken()`, then only invokes `unauthorizedHandler` when `hadToken` was true. This does not create a silent-swallow bypass — every 401 still (a) clears the token if present, and (b) rejects the promise via `Promise.reject(error)` unconditionally, so the calling code (`normalizeError` path in each exported function) still sees and surfaces the 401 to the user. The guard only dedupes the **handler invocation** (the redirect-to-login side effect) across a race of concurrently in-flight requests that all 401 after the token was already cleared by the first — it does not swallow the error response itself. Confirmed via `userApi.auth.test.js` TC-09 (second 401 does not double-invoke the handler) and TC-04 (first 401 clears token + fires handler + promise still rejects).

**Data**
- No PII in logs: the only new `console.log` call sites are `console.log("auth_session_expired")` in both `userApi.js:80` (response-interceptor path) and `App.jsx:73` (mount-time expiry path) — a bare string literal with no interpolated token, header, or user-identifying value. Verified by grep across the diff (`console.log\(` — 2 hits, both the literal string). `userApi.auth.test.js` TC-13 asserts the log call's arguments never match the raw token value.
- Token storage in `localStorage` (`TOKEN_KEY = "auth_token"`) is a known, accepted XSS-exposure tradeoff already documented in AUTH-04's Decision log / NFR-Security (per the story's own risk acceptance) — re-confirmed present and unchanged in this diff; not re-raised as a new finding per the task's guidance. No additional sensitive values (passwords, PII) are ever written alongside the token — `userApi.auth.test.js` TC-12 asserts `localStorage.length === 1` after `setAuthToken`, i.e. only the opaque token is persisted under that key.
- `setAuthToken`/`getStoredToken`/`clearAuthToken` all fail closed and fail readable: `localStorage` exceptions are caught and either return `null` or throw a readable `Error` (never a raw `DOMException` or stack trace) — consistent with the project-wide "never surface raw stack traces" convention (CLAUDE.md § Conventions).

**Input**
- No new untrusted-input trust-boundary crossing is introduced — the only new input processed is the JWT string already held client-side (from `localStorage`, written by the app's own `setAuthToken`), decoded defensively.

**Crypto**
- No new crypto primitives introduced. `jwt-decode` performs no cryptographic verification (by design — it is a decode-only library); this matches the ADR-2 rationale and the story's server-side-verification model. No `algorithm: none` acceptance, no signature-bypass logic anywhere in the diff.

**React stack-pattern pass**
- `userApi.js` remains the sole module touching `localStorage`/axios; `App.jsx` calls only through `userApi`'s exported surface — matches the layering rule in `react-patterns` (services as the only HTTP/storage entry point).
- No component calls `axios` directly; no raw error/stack trace surfaced to the UI from the new auth code paths.
