## High findings

### F-01 — `PyJWT==2.9.0` (new dependency, ADR-5) — RFC 7515 `crit` header not validated

- Source: `deps-scan/pip-audit`
- Severity: High
- Package: `pyjwt@2.9.0`
- Advisory: `CVE-2026-32597` / `GHSA-752w-5fwx-jx9f` (`PYSEC-2026-120`)
- Fixed in: `2.12.0` (project should target the latest `2.13.0` — see Medium/Low findings below, which are fixed only as of `2.13.0`)
- Description: PyJWT does not reject JWS tokens whose header carries an unknown `crit` (RFC 7515 §4.1.11 "MUST reject if unrecognized") extension — it silently accepts and decodes them instead. The advisory explicitly compares this to CVE-2025-59420 (Authlib), scored CVSS 7.5 (High).
- Applicability in this diff: `AuthService._issue_token` only *encodes* tokens today (`jwt.encode(...)`); no production route in this diff calls `jwt.decode()` to verify an inbound token (`test_auth.py`'s `jwt.decode(...)` call is test-only, decoding a token this same process just signed). The vulnerability is therefore **not currently reachable** through any shipped endpoint in AUTH-02. However: (a) PyJWT is a new dependency introduced by this diff specifically to become the project's JWT library, (b) `docs/features/AUTH-02/PLAN.md` ADR-5's own risk assessment states "no CVEs at the pinned version" — that statement is now factually incorrect and should be corrected before other AUTH-epic stories (e.g. AUTH-06 `GET /api/auth/me`, or any future server-side token-verification endpoint) build a `jwt.decode()` call path on top of this same pinned version, and (c) per `security-assessment`'s rule "never reclassify severity to force PASS," a High-class CVE in a newly-pinned security-critical library is reported at its CVSS-comparable severity regardless of today's reachability.
- Fix: bump `PyJWT` to `>=2.13.0` in `backend/requirements.txt` (also closes the Medium/Low PyJWT findings below) before any story adds server-side `jwt.decode()` verification.

## Medium findings

### F-02 — `PyJWT==2.9.0` — verifier-side algorithm allow-list bypass via `PyJWK`

- Source: `deps-scan/pip-audit`
- Severity: Medium (downgraded from the advisory's own "High attack-complexity" framing — see Applicability)
- Package: `pyjwt@2.9.0`
- Advisory: `CVE-2026-48523` / `GHSA-jq35-7prp-9v3f` (`PYSEC-2026-176`)
- Fixed in: `2.13.0`
- Description: when `jwt.decode()`/`decode_complete()` is called with a `PyJWK` key object and the caller allows both HMAC and asymmetric algorithms, the verifier checks the header `alg` against the allow-list but actually verifies using the algorithm bound to the `PyJWK`, not the header's `alg` — allowing an attacker who controls a registered JWK to sign with a disallowed algorithm and still pass.
- Applicability: this codebase never constructs a `PyJWK` object, never uses `PyJWKClient`, and `AuthService` verifies nothing server-side (only encodes with a plain string secret + fixed `algorithm="HS256"`). Not reachable today.
- Fix: covered by the F-01 upgrade to `2.13.0`; do not adopt `PyJWKClient`/`PyJWK` with a mixed-algorithm allow-list without re-reviewing this advisory first.

### F-03 — (carried from `docs/features/AUTH-02/REVIEW.md` F-1) "Successful login" logged before token issuance can still fail

- Source: `checklist/logs-and-errors`
- Severity: Medium
- File: `backend/app/services/auth_service.py:73-74`
- Description: `logger.info("Successful login", extra={"user_id": user.id})` fires immediately after credential verification, before `_issue_token()` runs — a call that can itself raise `HTTPException(500)` (e.g. `JWT_SECRET_KEY` unset, per `test_login_fails_generically_when_jwt_secret_key_is_unset`). In that path the audit trail records a "successful login" for a request that ultimately failed and returned no token.
- Audit-log-forgery assessment (explicitly requested): this is **not** an exploitable forgery vector. The log entry's `user_id` and outcome are still derived from real, already-verified credentials — an attacker cannot use this ordering to inject an arbitrary/forged log line for an account they don't control, and the failure mode requires `JWT_SECRET_KEY` to be unset, which `AUTH-08`'s startup fail-fast check is designed to prevent. It is an audit-*accuracy* defect (an operator/SIEM could over-trust a "successful login" that didn't actually complete), not an authentication or log-integrity bypass. Non-blocking.
- Fix (already on file in REVIEW.md, unchanged here): move the `logger.info` call to after `_issue_token()` returns successfully.

### F-04 — (carried from `docs/features/AUTH-02/REVIEW.md` F-3) Login rate limiter keyed by hashed email only, not email+IP

- Source: `checklist/authentication-and-authorization`
- Severity: Medium
- File: `backend/app/services/auth_service.py:35-37,159-180`
- Rule: `.claude/rules/security-baseline.md` § Rate limit ("throttled per (hashed) email **AND IP**, default 3/email/60min rolling")
- Description: `AuthService`'s in-process limiter keys only on `sha256(strip().lower(email))`. An attacker rotating target emails from a single IP is unconstrained by this limiter (email dimension only); conversely a shared/NAT'd IP with one locked-out account does not affect other accounts (correct isolation on that axis, at least).
- Bypass-vector check (explicitly requested): confirmed **no case-sensitivity or whitespace bypass** — `_hash_email` normalizes via `.strip().lower()` before hashing (`backend/app/services/auth_service.py:52-54`), so `" User@Example.com "`, `"user@example.com"`, and `"USER@EXAMPLE.COM"` all collapse to the same rate-limit bucket. The only real gap is the missing IP dimension, which is the same gap already surfaced and formally accepted in `docs/features/AUTH-02/PLAN.md` ADR-2 (research condition C-4, GO-WITH-CONDITIONS) and REVIEW.md F-3.
- `pending_carry_forward` check: `docs/features/AUTH-02/state.json` `.pending_carry_forward` is `[]` — this deviation is tracked via ADR-2 + REVIEW.md, not as a state-machine carry-forward entry, and carries no compliance tag. It does **not** trigger the carry-forward-enforcement BLOCKED rule.
- Verdict on this item alone: accepted risk, not a new blocker — no code change required to merge; track IP-dimension rate-limiting as a follow-up once a shared cache/store exists (as REVIEW.md already recommends).

### F-11 — `set_initial_password.py` prints the operator-supplied email to stdout on success

- Source: `sast/print-pii` (checklist "Data" category, `print\([^)]*\bemail\b`)
- Severity: Low (downgraded from the pattern's default High after verifying a safe context — see below)
- File: `backend/app/scripts/set_initial_password.py:141`
- Matched: `print(f"Password set for user {_sanitize_email_for_output(email)}")`
- Context verified safe: (1) this is interactive CLI stdout, not a persisted application log/telemetry sink — it is never captured by `logging`, never sent anywhere the AC5/NFR log-hygiene tests police (`test_script_never_logs_or_prints_the_plaintext_password` explicitly asserts the *password* never appears in stdout/stderr/`caplog`, and deliberately does **not** assert the email is absent — confirming this output shape is intentional, reviewed design, not an oversight); (2) the email printed is the same value the operator just typed as `argv[1]` — no new information is disclosed to them; (3) `_sanitize_email_for_output` strips control characters, closing a terminal/log-injection angle; (4) the script has no HTTP-reachable surface (confirmed — not imported by `main.py` or any `api/` router) and per ADR-3 requires direct server/deployment access to invoke at all.
- Fix: none required; this is by design. If a future change pipes this script's stdout into a centralized log aggregator, revisit under the security-baseline's "no PII in logs" rule at that time.

## What went well

- `_hash_email` normalizes email (`strip().lower()`) before rate-limit keying and before hashing for the failed-attempt bucket — closes the case-sensitivity/whitespace bypass vector this review specifically checked for.
- JWT payload is exactly `{sub, exp}` (ADR-5) — no PII beyond the login-identifying email already returned by other authenticated endpoints, no role/permission claims that would need "least privilege" scoping.
- `algorithm="HS256"` is passed explicitly to both `jwt.encode` (production) and the test's `jwt.decode(..., algorithms=["HS256"])` — no `alg: none`, no algorithm-confusion surface (asymmetric algorithms are never registered as acceptable).
- `JWT_SECRET_KEY` is read exclusively via `os.getenv("JWT_SECRET_KEY")` at call time inside `_issue_token` — never hardcoded, never cached at import time, never logged; missing-secret path returns a generic 500 with no `jwt`/`os.environ` exception text (confirmed by `test_login_fails_generically_when_jwt_secret_key_is_unset`).
- AC5's `set_initial_password.py` reads the password exclusively via `getpass.getpass()`, never as `argv`/env var; confirmed no HTTP route registers it.
- AC4's placeholder hash (`_generate_unusable_hash`) is seeded with `secrets.token_urlsafe(32)` (256 bits of CSPRNG entropy) as the hash input — genuinely unguessable/underivable — and `_verify_credentials` gates on `must_reset_password` after computing (not skipping) the hash comparison, which is a deliberate timing-safety choice (constant work across "no user" / "wrong password" / "must-reset user" paths), not a defect.
- Generic 401 (`INVALID_CREDENTIALS_MESSAGE`) is byte-for-byte identical for unknown-email, wrong-password, and unprovisioned-account cases, confirmed by dedicated tests.
- No `eval`/`exec`/shell-injection/SQL-string-concatenation/`innerHTML` patterns found in the diff.
