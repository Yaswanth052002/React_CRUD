## Medium findings

### F-1 — "Successful login" logged before token issuance can still fail (carried forward, still present)

- Source: `checklist/logs-and-errors`
- Severity: Medium
- File: `backend/app/services/auth_service.py:67-68`
- Current code (unchanged since prior review):
  ```python
  logger.info("Successful login", extra={"user_id": user.id})
  token = self._issue_token(user.email)
  ```
- `_issue_token` can still raise `HTTPException(500)` (e.g. `JWT_SECRET_KEY` unset), so the audit log can record a "successful login" for a request that ultimately failed and returned no token. Not an exploitable forgery vector (the logged `user_id` is derived from already-verified credentials); it is an audit-accuracy defect, not an authn/authz bypass.
- Fix (unchanged recommendation): move `logger.info` to after `_issue_token()` returns successfully.
- Status: still open, non-blocking, same as `REVIEW.md` F-1.

### F-2 — Login rate limiter keyed by hashed email only, not email+IP (carried forward, still present)

- Source: `checklist/authentication-and-authorization`
- Severity: Medium
- File: `backend/app/services/auth_service.py:46,58-59,137`
- Rule: `.claude/rules/security-baseline.md` § Rate limit ("throttled per (hashed) email **AND IP**, default 3/email/60min rolling")
- `_hash_email(email)` (line 46) still normalizes via `.strip().lower()` before hashing — no case/whitespace bypass — but the limiter has no IP dimension. This is the same accepted risk already tracked in `docs/features/AUTH-02/PLAN.md` ADR-2 (research condition C-4, GO-WITH-CONDITIONS) and `REVIEW.md` F-3.
- `pending_carry_forward` in `state.json` is `[]` — this deviation is tracked via ADR-2/REVIEW.md, not a state-machine carry-forward entry, and carries no compliance tag, so it does not trigger the carry-forward-enforcement BLOCKED rule.
- Status: still open, accepted risk, non-blocking — same as prior review.
