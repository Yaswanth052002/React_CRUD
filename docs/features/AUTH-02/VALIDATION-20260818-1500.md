### End-to-end JWT verification (explicit ask)

Ran a real login against the live uvicorn server (not `TestClient`) with a provisioned user, to confirm the full chain works with AUTH-08's fail-fast var and AUTH-03's real bcrypt hashing in place simultaneously:

1. Provisioned `john@test.com` with a real password via `python -m app.scripts.set_initial_password john@test.com` (bcrypt hash written, per AUTH-03).
2. `POST http://127.0.0.1:8000/api/auth/login` with the correct credentials → `200 {"token": "eyJhbGci...six...ML QvH5Xg"}` — a genuine 3-part JWT.
3. Decoded with `jwt.decode(token, JWT_SECRET_KEY, algorithms=["HS256"])` → `{'sub': 'john@test.com', 'exp': 1787068666}`. Payload shape matches PLAN ADR-5 exactly: two claims only, `sub` (email) + `exp` (Unix timestamp, ~60 min out). No extraneous claims (no `role`, no `iat`).
4. Negative paths re-verified live: unknown email and wrong password both return `401 {"detail":"Invalid email or password."}` — byte-for-byte identical, matching TC-03/04's contract.
5. AUTH-08 fail-fast check verified directly: booting the app (via `TestClient` lifecycle, which triggers the `@app.on_event("startup")` handler the same way `uvicorn` does) with `JWT_SECRET_KEY` unset raises `RuntimeError: JWT_SECRET_KEY environment variable is required` — confirms AUTH-02's login flow genuinely depends on, and correctly fails without, this env var. (Note: a bare `python -c "import app.main"` does NOT trigger this check — the startup event only fires when the app is actually served. This is expected FastAPI lifecycle behavior, not a gap; the preflight step and the live-server stack smoke both exercise the real served path.)

No regressions found in this integration point.
