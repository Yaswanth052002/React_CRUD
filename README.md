# User Management CRUD Dashboard

A full-stack admin dashboard for managing user accounts — built with **React (Vite)** on the
frontend and **Python / FastAPI** on the backend, persisted to **SQLite**.

> **A note on "AgentRise™ Harness":** this project was requested for use with an "AgentRise
> Harness" CLI. That tool isn't something I have reliable knowledge of, and I didn't have
> network access while building this to look it up or install it — so I have **not** fabricated
> `harness` commands or config anywhere in this repo. See [Harness Workflow](#harness-workflow)
> below for how to wire it in once you confirm the real command set.

## 1. Project Overview

Administrators can create, view, update, delete, search, and filter user records from a
browser-based dashboard. All data is persisted in SQLite via SQLAlchemy — there is no
hardcoded or in-memory user data.

## 2. Architecture

```text
Browser (React UI)
      │  Axios (JSON over HTTP)
      ▼
FastAPI app  (app/main.py)
      │
      ▼
API routers   (app/api/*.py)          — parses requests, returns responses
      │
      ▼
Service layer (app/services/*.py)     — business rules (uniqueness, 404s)
      │
      ▼
Repository    (app/repositories/*.py) — all SQLAlchemy query logic
      │
      ▼
SQLAlchemy ORM → SQLite (users.db)
```

The frontend mirrors this separation: components never call Axios directly — every HTTP call
goes through `frontend/src/services/userApi.js`.

## 3. Technologies

**Frontend:** React 18, Vite, Axios, plain modern CSS (custom design system, no UI framework),
Vitest for tests.

**Backend:** Python 3.11+, FastAPI, Pydantic v2, SQLAlchemy 2.0, SQLite, Uvicorn, pytest +
httpx (via FastAPI's `TestClient`).

## 5. Prerequisites

- Python 3.11+
- Node.js 18+ and npm
- No external database needed — SQLite is a local file created automatically.

## 6. Backend Installation

```bash
cd backend
python3 -m venv .venv
source .venv/bin/activate        # Windows: .venv\Scripts\activate
pip install -r requirements.txt
cp .env.example .env             # adjust if needed
```

## 7. Frontend Installation

```bash
cd frontend
npm install
cp .env.example .env             # adjust VITE_API_URL if needed
```

## 8. Running the Backend

```bash
cd backend
source .venv/bin/activate
uvicorn app.main:app --reload
```

- API base URL: `http://localhost:8000`
- Interactive API docs (Swagger UI): `http://localhost:8000/docs`
- On first run, the `users` table is created and 5 sample users are seeded automatically.
  Restarting the server will **not** duplicate them.

## 9. Running the Frontend

```bash
cd frontend
npm run dev
```

- App URL: `http://localhost:5173`

Open `http://localhost:5173` in your browser — the dashboard loads live data from the FastAPI
backend on `http://localhost:8000`.

## 10. API Documentation

Base path: `/api`

| Method | Endpoint                | Description                                   |
|--------|--------------------------|------------------------------------------------|
| GET    | `/api/users`             | List users. Query params: `search`, `role`, `status` |
| GET    | `/api/users/{id}`        | Get one user                                   |
| POST   | `/api/users`              | Create a user                                  |
| PUT    | `/api/users/{id}`        | Update a user                                  |
| DELETE | `/api/users/{id}`        | Delete a user (returns `204 No Content`)       |
| GET    | `/api/dashboard/stats`   | `{ total_users, active_users, admin_users, regular_users }` |
| GET    | `/api/health`            | Basic health check                             |

Full interactive documentation (generated by FastAPI) is at `/docs` while the backend is
running.

**Request body for POST/PUT `/api/users`:**

```json
{
  "name": "John Smith",
  "email": "john@test.com",
  "phone": "9876543210",
  "role": "User",
  "status": "Active"
}
```

**Validation rules:** `name` ≥ 2 chars, `email` must be a valid address, `phone` must match
`^[0-9+\-() ]{7,20}$`, `role` ∈ `{Admin, User}`, `status` ∈ `{Active, Inactive}`, `email` must
be unique (a duplicate returns `409 Conflict`).

## 11. CRUD Usage (from the UI)

1. **Create** — click **+ Add User**, fill the form, submit. Validation runs client-side first;
   the server re-validates and rejects duplicate emails.
2. **Read** — the table loads from `GET /api/users` on page load and after every filter/search
   change. Click a row's view icon for the full detail view (`GET /api/users/{id}`).
3. **Update** — click a row's edit icon, change fields, submit (`PUT /api/users/{id}`).
4. **Delete** — click a row's delete icon → confirm in the dialog → `DELETE /api/users/{id}`.
5. **Search** — the search box filters by name, email, or phone (debounced, backend-driven).
6. **Filter** — the Role and Status dropdowns filter server-side alongside search.

Every mutation shows a loading state on its button, a success toast on completion, and a
readable error message (never a raw stack trace) on failure.

## 14. Troubleshooting

| Symptom | Likely cause / fix |
|---|---|
| Frontend shows "Could not reach the server" | Backend isn't running, or is on a different port than `VITE_API_URL` in `frontend/.env` |
| CORS error in browser console | Backend `CORS_ORIGINS` (in `backend/.env`) doesn't include your frontend's URL |
| `409 Conflict` on create/update | Email already exists on another user |
| `422` on create/update | Check the response body's `detail` — it names the invalid field |
| Table shows old data after edit | Shouldn't happen — the app refetches after every mutation. Hard-refresh if it persists |
| `users.db` has stale/no data | Delete `backend/users.db` and restart the backend to reseed |
| `pip install` fails | Make sure you're using Python 3.11+ and have activated the virtualenv |
| `npm install` fails | Make sure you're using Node.js 18+ |
